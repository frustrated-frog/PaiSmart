# PDF 上传重试幂等与本地管理员额度设计

## 问题

PDF 上传任务把“解析入库”和“向量化”放在同一个 Kafka 消费流程中。第一次执行已经保存父块和子块后，如果向量化失败，Kafka 会重试整个流程。解析逻辑再次从 `parent_index = 1` 插入，于是触发 `document_parent_chunks(file_md5, parent_index)` 唯一键冲突，并覆盖最初的失败原因。

本次实例的首个错误是 PaiSmart 应用内部 Embedding Token 余额不足，不是阿里云 API 账户余额不足：文档已完整解析为 481 个子块和 175 个父块，随后应用内部余额从批次扣减至 521，而下一批预计需要 2079。

## 目标

- Kafka 重试不得重复保存已经完整解析的父块和子块。
- 完整解析结果应被复用，重试只执行尚未完成的向量化阶段。
- 解析不完整时不得把残缺数据当作完成结果。
- 本地开发环境的管理员测试账户不受 PaiSmart 内部 LLM/Embedding Token 余额限制。
- 非本地环境和普通用户的额度控制保持不变。
- 页面应展示真正的失败原因，不再被后续唯一键冲突覆盖。

## 方案选择

### 采用：阶段感知的幂等消费

上传任务开始解析前，根据 `file_upload.estimated_chunk_count` 与 `document_vectors` 的实际数量判断解析结果是否完整，并确认父块存在：

- 实际子块数等于预估数且父块存在：跳过解析，直接进入向量化。
- 数量不一致或父块缺失：清理该 MD5 的残缺父块、子块和 Elasticsearch 数据，再重新解析。
- 首次任务没有任何解析数据：正常解析。

这既能复用本次已完整保存的 481 个切片，也能避免简单的“只要有一条就跳过”导致残缺文档被向量化。

### 未采用：忽略唯一键异常

仅捕获重复键会留下新旧父块 ID、子块关联和权限元数据不一致的问题，不能证明解析结果完整。

### 未采用：每次重试都删除并重新解析

虽然不会再出现重复键，但会重复执行耗时解析，也无法体现 Kafka 阶段重试语义。

## 本地管理员额度策略

在 `dev/local` 配置中加入明确的管理员额度绕过开关和管理员用户名。额度服务仅当以下条件同时满足时跳过内部余额检查和扣减：

- 本地绕过开关启用；
- 当前用户是配置的本地管理员；
- 数据库角色为 `ADMIN`。

生产配置默认关闭。阿里云 API 自身的鉴权、余额、限流和错误仍正常生效。

## 数据流

1. Kafka 收到上传任务并把文档状态设为处理中。
2. 幂等检查读取预估子块数、实际子块数和父块数。
3. 完整则跳过解析；残缺则清理后重新解析；不存在则首次解析。
4. 使用数据库中的子块执行向量化。
5. 成功后写入实际 Token、实际切片数和模型版本；失败时保留最初且可操作的错误原因。
6. Kafka 再次投递同一任务时重复上述判定，不产生重复父块。

## 测试与验收

- 单元测试：完整解析数据会跳过 `parseAndSave` 并调用向量化。
- 单元测试：残缺解析数据会先清理再重新解析。
- 单元测试：本地 ADMIN 绕过内部 LLM/Embedding 余额检查与扣减。
- 单元测试：普通用户以及关闭开关时仍执行原额度控制。
- 回归测试：同一上传任务执行两次，不出现父块唯一键冲突。
- 真实验证：对当前 MD5 发起向量化重试，状态最终为 `COMPLETED`，481 个子块与 175 个父块保持唯一，日志没有新的 `Duplicate entry` 或应用内部余额不足。

## 边界

- 不移除数据库唯一键。
- 不关闭生产环境额度控制。
- 不改变阿里云 API 的错误处理。
- 不删除用户上传的原始文件或已有完整解析结果。
