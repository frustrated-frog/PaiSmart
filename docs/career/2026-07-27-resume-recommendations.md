# 知枢项目简历增补建议

## 1. 结论

建议把 7 月 25 日至 27 日新增的内容写入简历，但不要把 45 个提交逐条罗列。对于后端岗位，最值得新增的是三组能力：

1. Agentic RAG 检索控制面：一次查询规划、多查询变体、BM25/Dense 独立召回、RRF 融合、可插拔重排、证据判断与纠正检索。
2. 可恢复 Agent Runtime：Run/Step/Checkpoint/Tool Ledger 持久化、硬预算、循环守卫、工具风险策略、审批与安全回放。
3. 真实轨迹评测与可观测性：从服务端持久化事实投影评测信号，建立检索指标、Agent 指标和质量门禁，并在前端展示执行轨迹与运行健康度。

这三点比“接入了大模型”“实现了 ReAct”更能体现后端工程深度，也与简历中美团的任务编排、京东的状态机、MQ、幂等和降级经验形成一致的技术主线。

## 2. 当前简历与新增代码的差距

简历 PDF 生成于 2026 年 7 月 21 日，早于本轮提交。当前项目部分已经写到：

- OpenAI-compatible `tool_calls` 和四个工具；
- 文件上传、解析、切片、向量化和 ES 入库；
- 中文语义切片、LiteParse/OCR 和 HanLP 兜底；
- Dense + BM25 rescore + 关键词匹配的基础混合检索。

本轮代码已经把项目从“会调用工具的 RAG 聊天”进一步推进为“有控制面、有运行时、有评测闭环的知识 Agent”，但这些内容还没有进入简历：

- QueryPlan 在 Run 入口只生成一次，并同时约束工具可见性和检索执行；
- BM25 与 Dense 对每个 query variant 独立并行执行，使用 RRF 融合异构排名；
- 检索结果经过重排、父子块上下文扩展、证据充分性判断和有界纠正召回；
- Agent 运行被模型轮次、工具数、Token 和墙钟时间四类预算约束；
- 工具调用具备风险、作用类型、并发策略、回放策略、动作指纹和持久化账本；
- 失败、中断、澄清和审批都能形成新的 attempt，并保留运行谱系；
- 检索和 Agent 轨迹都有确定性指标与门禁；
- 前端能查看 Query → Recall → RRF → Rerank → Evidence、预算、耗时、降级和恢复状态。

## 3. 推荐的简历项目段落

以下版本可以直接替换当前“企业知识库问答平台”项目描述。完整版本为 7 条；若版面不足，优先保留前 5 条中的第 1、2、3、5 条，再保留一条知识摄取能力。

### 企业知识库问答平台（知枢） 2026.04 - 2026.07

**技术栈：** Java 17、Spring Boot 3.4、Spring Data JPA/MySQL、Redis、Kafka、Elasticsearch 8、MinIO、WebSocket、Vue 3

- 基于 OpenAI-compatible `tool_calls` 设计企业知识 Agent，将查询规划结果作为单次 Run 的统一控制事实，按意图动态暴露知识检索、摘要、反馈和统计工具；构建有界 ReAct Runtime，以模型轮次、工具次数、Token 和执行时长硬预算约束不确定循环。
- 重构 Agentic RAG 检索链路，生成 ORIGINAL/LEXICAL/SEMANTIC/DECOMPOSED 多查询变体，在有界线程池中并行执行 Elasticsearch BM25 与 Dense 召回，通过 RRF 融合异构排名，并支持 HTTP Cross-encoder 重排及本地降级；所有通道前置同一套用户、公开范围和组织标签过滤。
- 实现证据判断与纠正检索闭环，根据查询/主题覆盖度、结果数量和保守冲突规则输出 SUFFICIENT/PARTIAL/INSUFFICIENT/CONFLICTED 状态；对缺失主题执行最多两轮差异化补检索，并用证据集合签名检测无进展，避免重复召回和无限循环。
- 以 MySQL 持久化 Agent Run/Step/Checkpoint/Tool Ledger，Redis 仅保存流式热状态；服务重启后将悬空任务标记为可重试中断，并通过 `retryOfGenerationId`、`attemptNumber` 和 checkpoint 创建独立新 attempt，支持跨刷新回放、澄清恢复和工具审批恢复。
- 建立工具治理与故障隔离机制，为工具声明风险等级、读写副作用、并发和回放策略；结合动作指纹、唯一约束、用户级 Semaphore、独立线程池、超时熔断、类型化错误与敏感信息脱敏，避免非幂等工具重复执行和异常信息泄露。
- 建立检索与 Agent 真实轨迹评测框架，从服务端 Run/Step/Tool Ledger 投影事实，计算 Recall@K、MRR、nDCG、P95、轨迹得分、工具选择/参数准确率、恢复成功率和重复副作用率，并通过可配置阈值形成质量门禁和可视化运行健康面板。
- 构建企业知识摄取 Pipeline，支持大文件分片上传、MinIO 合并、Embedding Token 预估、Kafka 异步解析与向量化；普通文档使用 Tika 流式解析，PDF 使用 LiteParse/OCR 保留页码，结合父子分块和 overlap 兼顾精确召回与生成上下文完整性。

## 4. 更短的四条版本

如果项目区只能保留四条，建议使用这一版：

- 设计并实现可控 Agentic RAG：以一次性 QueryPlan 驱动意图路由与 Multi-query，在 Elasticsearch 中独立并行执行 BM25/Dense 召回，使用 RRF 融合、可插拔重排、父子块扩展及证据纠正检索构建可解释检索链路。
- 构建有界 ReAct Runtime，通过模型轮次、工具数、Token、时长预算和语义循环守卫防止失控；为工具声明风险/副作用/并发/回放策略，并结合动作指纹、持久化账本、人工审批与熔断隔离保障工具执行安全。
- 以 MySQL Run/Step/Checkpoint 作为运行事实源、Redis 作为流式热状态，实现断线续传、澄清恢复、服务重启后中断识别以及基于 checkpoint 的新 attempt 重试，保留完整执行和计费谱系。
- 建立检索与 Agent 轨迹评测框架，覆盖 Recall@K、MRR、nDCG、P95、工具选择、引用、恢复和重复副作用等指标，并在 Vue 端展示检索 Trace、预算、降级和运行健康度。

## 5. 一分钟项目介绍

> 知枢是我基于开源企业知识库做的二次开发。我保留了原项目的文档上传、向量化和聊天基础能力，重点把传统 RAG 改造成可控的 Agentic RAG。一次请求先生成结构化 QueryPlan，再对多个查询变体并行执行 BM25 和 Dense 召回，用 RRF 融合、重排和父子块扩展构建证据；如果证据不足，会做有界的纠正检索。运行时则把模型当作语义决策者，把权限、预算、状态迁移、工具副作用和审计交给后端确定性逻辑。每次 Run、Step、Checkpoint 和工具动作都落 MySQL，Redis 只保存短期流式状态，因此失败、澄清和审批都能沿运行谱系恢复。我还补了基于真实持久化轨迹的离线评测和前端 Trace 面板，使优化可以被测量和复盘。

## 6. 面试时必须主动说明的边界

这些边界说明会增加可信度，避免被追问时被动降级：

- 不要说“实现了通用分布式工作流引擎”。当前是领域化的单 Agent Java Runtime，恢复通过新 attempt 和 checkpoint 重建，而不是任意节点的透明分布式续跑。
- 不要直接说“Cross-encoder 已在线提升 nDCG”。代码提供 HTTP Cross-encoder 接口，但默认未配置时使用本地启发式重排；只有补齐真实消融数据后才能写提升比例。
- 不要说“证据判断解决了幻觉”。当前判断器主要基于确定性的词项覆盖、结果量和保守冲突规则，它能决定补检索/部分回答/放弃，但不能替代严格的 claim-level entailment。
- 不要写尚未测量的 Recall、P95、成功率或成本降幅。仓库已有指标计算和黄金集样例，但简历数字应来自固定数据集、固定 commit、固定模型和固定环境的实际运行。
- 不要把开源基线能力都说成自己从零开发。推荐表述是“基于开源项目二次开发，独立完成 Agentic RAG 与 Agent Runtime 增强”。

## 8. 简历本身的额外修改建议

- 当前专业技能区偏长，且大量使用“深刻理解”。建议压缩基础知识，把版面让给能被代码和指标证明的项目成果。
- “TUP”应改为“TCP”；“ConcurrrentHashMap”应改为“ConcurrentHashMap”。
- 项目技术栈应补充 Spring Data JPA；新 Agent 运行账本代码主要通过 JPA Repository 持久化，不能只写 MyBatis。
- “产研一体”不是标准角色描述，建议改为“个人项目 / 二次开发”，并在项目介绍第一句明确开源基线与个人新增范围。
